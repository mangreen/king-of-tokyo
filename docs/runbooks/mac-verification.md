### 發現的問題與修正（已修正，已重新驗證）

1. **esbuild 在 Big Sur 無法安裝。** esbuild 0.27 起的 macOS 二進位檔最低需要 macOS 12。已改為 tsx 4.20.6、tsup 8.5.0（它們相容 esbuild 0.25.12，最低 macOS 11），並加上 `pnpm run check:baseline` 防止日後回退。lockfile 裡其他三個 macOS 原生套件（rolldown、rollup、lightningcss）最低只要 macOS 10.12–10.13。
2. **Snyk 容器掃描的高風險項目不是我們的程式碼。** 掃描結果中 33 個與 24 個問題的專案名稱是 `dist`（corepack 下載的 pnpm）與 `lib`（base image 的 npm）。我們自己的依賴（專案 `king-of-tokyo`）與 Alpine 系統套件都是乾淨的。已改成乾淨的 runtime 映像，不帶 pnpm、npm、yarn、corepack。

## M2 實測清單（分支 `m2/lobby-and-connection`）

沙盒已用 Playwright 開兩個瀏覽器跑過：建房 → 加入 → 準備 → 開始 → 打完一局 → 重新整理頁面接回。以下需要在你的 Mac 與真實瀏覽器上確認。

```bash
git fetch origin && git checkout m2/lobby-and-connection && git pull
pnpm install --frozen-lockfile
pnpm run check
docker compose up --build        # 或：pnpm run dev:server 與 pnpm run dev:web 各開一個終端機
```

1. 開兩個瀏覽器視窗（其中一個用無痕視窗，因為身分存在 sessionStorage，同一分頁的不同視窗不會共用，但無痕更保險）到 http://localhost:5173。
2. 視窗 A 輸入暱稱 → 建立房間，記下 5 碼房號；視窗 B 輸入另一個暱稱 → 用房號加入 → 按「準備」。
3. A 按「開始遊戲」。預期：兩邊都看到玩家表、東京市、倒數計時；輪到的人可以「擲骰／重擲／結算」，點骰子可保留。
4. **重連：** 對局中在 B 按重新整理。預期：回到同一座位的對局畫面（事件日誌會是空的，這是預期行為）。
5. **逾時代打：** 輪到某位玩家時什麼都不做，等 45 秒。預期：標示「代打中」，系統代打；之後那位玩家再按任何合法動作就會取回控制。
6. **斷線：** 對局中關掉 B 的分頁。預期：A 看到 B「離線」，輪到 B 時約 1.5 秒就被代打。
7. 手機同一個 Wi-Fi：把 `.env` 的 `ALLOWED_ORIGINS` 加上 `http://<你的 Mac 區網 IP>:5173`，並把 `VITE_SERVER_URL` 改成 `http://<IP>:3001`，用手機瀏覽器開（選配）。

請回報：`pnpm run check` 是否通過、第 3–6 步是否符合預期（失敗請貼瀏覽器 Console 的錯誤，**不要貼含 sessionToken 的內容**）。

## 1. 更新並重新安裝

```bash
cd king-of-tokyo
git fetch origin
git checkout m0/skeleton && git pull
rm -rf node_modules apps/*/node_modules packages/*/node_modules
corepack enable          # 第一次會問是否下載 pnpm 10.28.0，回答 y
pnpm install --frozen-lockfile
```

預期：安裝成功，沒有 `postinstall failed`。可能會看到 `unmet peer esbuild` 的警告，這是 vite 的**選用** peer，不影響執行。

```bash
pnpm run check           # 預期全部通過，最前面印出「基準機相容性檢查通過」
```

## 2. Docker 開發環境

```bash
cp .env.example .env     # 已有 .env 就略過
docker compose up --build
curl http://localhost:3001/healthz     # 預期 {"status":"ok"}
```

瀏覽器開 http://localhost:5173 ，預期顯示「已連線（連線 ID：xxxxxxxx）」。

停止：`docker compose down`（加 `-v` 會一併刪除資料庫資料）。

## 3. 正式 server 映像（這次改了，沒有實機驗證）

```bash

docker run --rm -p 3001:3001 kot-server &
sleep 2
curl http://localhost:3001/healthz     # 預期 {"status":"ok"}
docker stop $(docker ps -q --filter ancestor=kot-server)
docker run --rm kot-server sh -c 'which npm pnpm yarn corepack || echo "沒有套件管理器（預期）"'
```

## 4. 依賴安全掃描

Snyk CLI 在 Big Sur 上只能降級執行。建議順序：

```bash
# a) 容器（可執行）。預期不再出現專案 dist / lib
snyk container test kot-server

# b) 依賴：需要 --all-projects（monorepo）。若 CLI 因 macOS 版本無法執行，改用 c) 或 d)
snyk test --all-projects

# c) 任何環境都能執行
pnpm audit --prod

# d) 在 Snyk 網站匯入 GitHub repo mangreen/king-of-tokyo（不需要本機 CLI）
#    Snyk Code（SAST）需先到 Settings > Snyk Code 啟用
```

沙盒中的 `pnpm audit --prod` 結果：**沒有已知漏洞**（2026-11-06）；含 dev 依賴有 1 個中等風險（`eslint` 內的 `minimatch`，不會進入任何映像）。

請把高風險（high/critical）的結果貼回來。Token 只放在環境變數，不要寫進檔案或提交。

## 跟隨按鈕修正驗證（拖曳地圖後；尚未實測）

1. 開著跟隨（🎥 綠色）時拖曳／縮放地圖：🎥 變成灰底綠色虛線框（暫停），出現 ↺。
2. 此時按 🎥：視角重置、鏡頭回到跟隨、🎥 變綠；不會被關掉。按 ↺ 也會重置視角並回到跟隨。
3. 在綠色狀態再按一次 🎥 才是關閉（灰色）。下方「鏡頭跟隨」勾選框的行為相同。

## M4.10 驗證清單（怪獸造型隨機分配；尚未實測）

1. 同一個房間連玩幾場：每場每位玩家的怪獸不同，同一場內不重複；所有玩家看到的同一個人是同一隻怪獸。
2. 玩家列表每個人名字旁顯示怪獸名稱，與 3D 場景中的造型相符。
3. 12 種造型都至少出現一次：外型辨識度、大小是否一致、名牌位置是否正常；從總覽與跟隨鏡頭看都沒有被建築擋住。
4. 12 種怪獸各攻擊一次，招式特效都正常（含新增的水柱、鐮刀斬、冰霜、震地、孢子、凝視光束）。
5. 基準機（2014 MBP）：6 人局抽到面數較多的造型時 FPS 是否仍 ≥30。

## M6 驗證清單（房主模式；尚未實測）

1. 伺服器模式照舊（登入、建房、玩一局）沒壞。
2. 開 `http://localhost:5173/?mode=p2p`（server 要在跑）：頁面上方有「房主模式」提示。輸入暱稱、**房號欄留空**、按「當房主」→「建立房間」，房間頁出現分享連結。
3. 用**另一個瀏覽器（或無痕視窗）**開分享連結，輸入暱稱加入。兩邊都看得到彼此；房主按「加入電腦」，雙方準備後開始遊戲。
4. 玩一局：兩邊的畫面同步；Network 面板：房主與客人各有**一條** WebSocket 連到 server，**沒有**其他連線。
5. 客人重新整理頁面：回到登入畫面（預期，M8 才做接回）；用同一個連結重新加入，房間還在。
6. 房主關閉分頁：客人約 30 秒後看到連線結束的提示。
7. 用手機開分享連結當客人，回報是否能完整玩完一局，以及延遲感受（多一跳經過 server）。
8. （可選）房主用手機：回報螢幕關閉或切到別的 app 後，房間是否中斷。

## M5 驗證清單（離線模式與可攜核心；尚未實測）

1. 先確認伺服器模式沒壞：照原本流程登入、建房、加電腦、開局、玩一局。
2. 開 `http://localhost:5173/?offline=1`：頁面上方有「離線模式」提示。**停掉 server（`docker compose stop server`）後也能用**：輸入暱稱、建立房間、加入 2 個電腦玩家、開始遊戲，一路玩到結束。
3. 離線模式下開瀏覽器開發者工具的 Network：**沒有 WebSocket 連線**，也沒有對 server 的請求。
4. 離線局中重新整理頁面：回到登入畫面（這局結束），**不會**自動接回（預期行為，M8 才做接回）。
5. 基準機上觀察：離線模式 6 人局（1 真人＋5 電腦）的 FPS 與 CPU；電腦玩家的計算在 Worker，畫面應該不會因為電腦思考而卡住。
6. 手機瀏覽器開同一個離線網址試玩，回報是否能完整玩完一局。

## M4.14 驗證清單（閒置踢除；尚未實測）

1. 登入後把分頁丟著不動（試玩版 5 分鐘、本機預設 10 分鐘）：畫面出現「閒置太久，已中斷連線」與「重新連線」「登出」兩個按鈕，**不會自動重連**。
2. 按「重新連線」：回到原本的房間／座位（對局中也一樣）。
3. 一直有操作（移動滑鼠、轉動鏡頭）超過上限時間：不會被踢。
4. 分頁切到背景超過上限：被踢（預期行為）；切回來看到「重新連線」。
5. 對局中閒置被踢：你的角色由代管接手，其他人照常進行。
6. Cloud Run：部署後放一天，看「容器執行個體時間」與「請求數」是否比以前低（以前沒有基準，只能看是否不再爆表）。

## M4.13 驗證清單（電腦玩家；尚未實測）

1. 建立房間後，房間頁只有房主看得到「🤖 加入電腦」；按一下多一位「電腦 N」（有 🤖 標籤、已準備），旁邊有「移除」。真人加電腦滿 6 位時按鈕變灰。
2. 只有房主一人時「開始遊戲」是灰的；加一台電腦就能開局。非房主（用邀請連結加入的朋友）看得到電腦但沒有加入／移除按鈕。
3. 開局後輪到電腦時：約 1.4 秒後自動擲骰、保留骰子、重擲、結算、買牌；3D 演出跟得上、不會一次噴出一堆動畫。玩家列表有 🤖 標籤，沒有「代打中」，也沒有倒數秒數。
4. 電腦在東京被打時會自己決定讓位；血量低時傾向離開。
5. 你自己閒置：你被標成「代打中」（用較弱的固定策略），電腦不受影響。
6. 只剩電腦（真人都離開）時房間會關閉，不會留下一場沒人看的對局。
7. 多打幾場：電腦是否「看起來合理」（不會自殺式亂買牌、不會一直待在東京被打死）；有任何明顯不合理的決定請記下局面回報，這些會是調整 `ai.ts` 權重的依據。
8. 基準機（2014 MBP）：對局中有電腦時 FPS 與沒有電腦時相比有無差異（電腦的計算在伺服器，網頁端不應受影響）。

## M4.12 驗證清單（邀請連結；尚未實測）

1. 房主在房間頁按「複製連結」，貼到別處確認是 `https://網址/?room=房號`。手機上按「分享…」能叫出系統分享選單。
2. 另一台裝置（或無痕視窗）開連結：看到「你被邀請加入房間 XXXXX」，輸入暱稱後直接進入房間，房主那邊立刻看到新玩家。
3. 加入後網址上的 `?room=` 消失；重新整理仍在房間內。
4. 連結的房間已開始遊戲、已滿或不存在：回到大廳並顯示原因，不會卡住。
5. 已經登入的分頁開邀請連結：直接加入（若本來就在別的房間內則不動）。
