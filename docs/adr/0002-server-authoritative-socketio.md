# ADR-0002：伺服器權威架構與 Socket.IO

- 狀態：已採用（2026-11-05）

## 背景

這是一款回合制、含隱藏資訊（牌堆順序）與隨機（骰子）的多人遊戲。目標容量為**同時 10,000 人在線**（使用者指定）。玩家之間是朋友，但仍需防止竄改（例如修改客戶端自行決定骰子結果）。

## 選項

1. 客戶端權威或點對點：實作最簡單，但無法防作弊、無法保證骰子與牌堆公平。
2. 伺服器權威 + 原生 `ws`：最輕量，但房間、心跳、重連都要自己做。
3. 伺服器權威 + Socket.IO：內建房間、心跳、自動重連、傳輸降級。
4. 遊戲框架（如 Colyseus）：功能完整，但綁定框架的狀態同步模型。

## 決策

選 **3：伺服器權威 + Socket.IO（搭配 Fastify）**。

- 客戶端只送「意圖」（例如保留哪幾顆骰子、購買哪張卡）；伺服器驗證合法性、擲骰（以 `crypto` 產生 seed）、推進規則引擎，再廣播**每位玩家視角**的狀態（牌堆順序不外洩）。
- 規則引擎是純函式庫（`@kot/rules`），狀態包含 RNG 狀態，可由「初始 seed + action log」完整重放。
- 所有訊息以 zod 驗證，協定帶版本號（`PROTOCOL_VERSION`），不相容時握手即拒絕。
- 伺服器端檢查 `Origin`、限制單則訊息大小、握手逾時中斷。

## 容量與擴展

- 回合制遊戲的訊息量很低，CPU 不是瓶頸；**連線數與記憶體**才是。10,000 連線約對應 2,000 個五人房間。
- MVP 為**單一實例、房間狀態放記憶體**。這不代表已證明能撐住 10,000 人：M5 必須用 Linux 環境做負載測試（連線數、記憶體、事件延遲），並調整作業系統的檔案描述符上限。
- 若單實例不夠：以房間為單位分片（房號決定所在實例，需 sticky routing），必要時加入 Redis adapter。這是現在刻意**不做**的複雜度。
- 單實例的代價是重啟會中斷進行中的對局。對局事件日誌（M5）會讓伺服器可以由 seed + action log 恢復房間。

## 影響

- 所有規則邏輯必須在伺服器執行，客戶端的規則程式碼僅用於 UI 提示（例如預覽合法動作），不能作為依據。
- 重連需要 session token（M2），而不是依賴 Socket.IO 的 socket id。
- 需要在 M2 加入限流（rate limit），M0 只有訊息大小上限與握手逾時。
